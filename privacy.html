5.2 IP Address Handling — Special Note

IP addresses are a necessary technical element of internet communication — without them, your browser cannot receive the pages it requests. However, Indo Pakhtoon Tech applies the following privacy-protective practices to IP address data:

  • IP Anonymization: Where technically configurable (particularly in Google Analytics), IP anonymization (IP masking) is enabled so that the full IP address is never stored in analytics systems — only the network-level prefix is retained for geographic region analytics;
  • No User Profiling: IP addresses in server logs are not used to build profiles of individual users or to track browsing behavior over time;
  • Security Exception: In cases of detected malicious activity, DDoS attacks, or abuse, specific IP addresses may be temporarily logged and blocked as part of our security response, in compliance with applicable law;
  • Retention Limitation: Raw server log files containing IP addresses are not retained beyond the period necessary for security and operational purposes, as described in our Data Retention Policy (Section 13).

5.3 Anonymized Analytics

Indo Pakhtoon Tech uses anonymized, aggregated analytics data to understand how users interact with the Platform and to make informed decisions about feature development and performance optimization. Key characteristics of our analytics approach:

  • Analytics data is collected and processed in aggregated, non-identifiable form;
  • No analytics data is linked to a named or otherwise identifiable individual;
  • Analytics is used exclusively for Platform improvement — never for advertising targeting or third-party sharing;
  • Users may opt out of analytics tracking through browser privacy settings, Google Analytics Opt-Out tools, or ad-tracking opt-out settings on Android devices.

7.3 How UPI Payments Work — Privacy Architecture

When you make a UPI donation to Indo Pakhtoon Tech, the payment flow works as follows, and Indo Pakhtoon Tech is deliberately positioned outside the sensitive portions of this flow:

  1. You initiate the payment in your own UPI-enabled app (Google Pay, PhonePe, BHIM, Paytm, bank UPI app, etc.);

  4. Indo Pakhtoon Tech receives only the transaction completion notification (if configured), which includes the UTR (Unique Transaction Reference) number, amount, and timestamp — none of which contain any sensitive financial credentials;
  5. The UTR is stored solely to enable refund processing if requested by the user within the refund window described in the Terms and Conditions.

Security & Anti-Abuse Protection Measures

Technical and organizational safeguards protecting the Platform and its users from malicious activity

Indo Pakhtoon Tech implements a layered set of security measures designed to protect the Platform's infrastructure, user data, and service availability against unauthorized access, malicious attacks, abuse, and data breaches.

12.1 Transport Security

  • HTTPS / TLS Enforcement: All communications between your browser or application and the Platform are encrypted using TLS (Transport Layer Security). HTTP connections are automatically redirected to HTTPS. HSTS (HTTP Strict Transport Security) headers are implemented to prevent protocol downgrade attacks;
  • Certificate Management: SSL/TLS certificates are maintained with current, trusted certificate authorities and renewed before expiration;
  • Secure API Communication: All API endpoints use HTTPS with certificate validation to prevent man-in-the-middle attacks.

12.2 Authentication Security

  • User authentication is delegated to Google OAuth 2.0 — an industry-hardened authentication protocol. Indo Pakhtoon Tech never handles, stores, or transmits user passwords;
  • OAuth tokens are stored securely using industry-standard token storage practices and are not exposed in URLs, client-side storage without appropriate protections, or server logs;
  • Session tokens are appropriately invalidated upon logout and subject to reasonable expiry periods.

12.3 Anti-Bot & Anti-Abuse Measures

  • Rate Limiting: API endpoints and form submissions are subject to rate limiting to prevent automated brute-force attacks, credential stuffing, and excessive automated requests;
  • CAPTCHA Integration: Where appropriate (such as contact forms or donation submission flows), CAPTCHA challenges (such as Google reCAPTCHA) are deployed to distinguish genuine users from automated bots;
  • IP-Based Blocking: IP addresses identified as sources of malicious traffic, DDoS attacks, or systematic abuse may be temporarily or permanently blocked at the network layer;
  • User-Agent Validation: Requests exhibiting characteristics of known malicious bots, scrapers, or automated attack tools may be filtered and blocked;
  • Web Application Firewall (WAF): A Web Application Firewall filters incoming HTTP/HTTPS traffic against known attack signatures, including SQL injection, Cross-Site Scripting (XSS), and Cross-Site Request Forgery (CSRF) attempts.

12.4 DDoS Protection

Indo Pakhtoon Tech employs infrastructure-level DDoS (Distributed Denial of Service) mitigation measures through its hosting provider to maintain Platform availability during volumetric attack events. These protections operate transparently at the network and application layer without affecting the experience of legitimate users.

12.5 Secure Development Practices

  • Third-party dependencies are regularly reviewed for known security vulnerabilities and updated promptly;
  • Code is reviewed for common security issues before deployment;
  • Android applications are developed in compliance with Android security best practices, including use of the Android Keystore for sensitive cryptographic operations and avoidance of insecure data storage patterns;
  • No sensitive configuration data (API keys, credentials) is embedded in publicly accessible application binaries or client-side code.

12.6 Data Breach Response

In the event of a security breach that results in or is likely to result in unauthorized access to, disclosure of, or loss of personal data, Indo Pakhtoon Tech will:

  • Take immediate steps to contain and remediate the breach;
  • Notify affected users without undue delay and, where required by the DPDPA 2023, within the timeframe prescribed by applicable regulation;
  • Notify the relevant Data Protection Board and other authorities as required by law;
  • Provide affected users with information about the nature of the breach, the data affected, the likely consequences, and the steps taken or proposed to address it;

Advertising ID & Cross-App Tracking Transparency

Full disclosure of how the Android Advertising ID is used and how users can control it

In ad-supported Indo Pakhtoon Tech Android applications, Google AdMob may use the Android Advertising ID (AAID) — a unique, resettable identifier assigned by the Android operating system — to serve advertisements and measure their effectiveness. This section provides complete transparency about how the Advertising ID is used and how you can control it.

22.1 What Is the Android Advertising ID?

The Android Advertising ID (also referred to as AAID or GAID — Google Advertising ID) is a unique, anonymous, resettable identifier provided by Google Play Services on Android devices. It was created specifically for advertising purposes to allow ad networks to serve relevant advertisements and measure ad performance without requiring access to more persistent and sensitive device identifiers (such as the hardware IMEI).

Key characteristics of the AAID:

  • It is not tied to your real identity — it is a random string of characters;
  • It is resettable — you can generate a new AAID at any time through Android settings, which effectively severs the link between your device and any advertising profile built on the old AAID;
  • It is opt-out capable — you can disable personalized advertising, which instructs all apps to use the AAID only for non-personalized advertising or frequency capping;
  • On Android 12 and above, if you opt out of personalized advertising, all zeros are returned as the AAID value, effectively making it non-functional for profiling.

22.2 How Indo Pakhtoon Tech Uses the AAID

Indo Pakhtoon Tech itself does not directly access, store, or process the Android Advertising ID. The AAID is accessed solely by the Google AdMob SDK integrated into supported applications, and its use is governed entirely by Google's advertising policies and Google's Privacy Policy. Indo Pakhtoon Tech does not:

  • Link the AAID to any personally identifiable information such as name, email, or account data;
  • Use the AAID for purposes other than ad serving and ad measurement through AdMob;
  • Share the AAID with any party other than Google AdMob's SDK through its normal operation;
  • Attempt to fingerprint devices or use the AAID in combination with other identifiers to circumvent user opt-out choices.

22.3 How to Control Your Advertising ID

Android users have full control over the Advertising ID through their device settings. The following steps apply (exact menu names may vary by Android version and device manufacturer):

  • 1 To opt out of personalized ads: Go to Settings → Google → Ads → Opt out of Ads Personalization (Android 11 and below) or Settings → Privacy → Ads (Android 12 and above).
  • 2 To reset your Advertising ID: Go to the same location and select "Reset Advertising ID" (Android 11 and below) or "Delete Advertising ID" (Android 12 and above, which replaces the ID with all zeros).
  • 3 To verify your opt-out status: The same settings page displays whether personalized advertising is enabled or disabled for your device.

Network Security & Protection of Data in Transit

Technical measures ensuring that all data exchanged between your device and the Platform remains secure at every stage of transmission

Every time your device communicates with the Indo Pakhtoon Tech Platform — whether you are loading a webpage, using a web-based calculator tool, authenticating via Google Sign-In, or submitting a support inquiry — data travels across the internet between your device and our servers. This section explains in detail how Indo Pakhtoon Tech protects that data in transit from interception, manipulation, and unauthorized access.

31.1 TLS Encryption — The Foundation of Data-in-Transit Security

All communications between users and the Indo Pakhtoon Tech Platform are encrypted using TLS (Transport Layer Security) — the successor to SSL and the industry standard for securing internet communications. TLS encryption ensures that:

  • Confidentiality: Data transmitted between your device and our servers cannot be read by any third party that intercepts the connection — including internet service providers, network operators, or malicious actors on public Wi-Fi networks;
  • Integrity: Data cannot be silently modified in transit — any tampering with encrypted data will cause the connection to fail, alerting both parties to the interference;
  • Authentication: TLS certificates verify that you are genuinely communicating with Indo Pakhtoon Tech's servers and not with an impersonator — preventing man-in-the-middle attacks.

31.2 TLS Protocol Version Standards

Indo Pakhtoon Tech enforces the use of modern, secure TLS protocol versions. Specifically:

  • TLS 1.2 and TLS 1.3 are the minimum accepted protocol versions — older, insecure versions (TLS 1.0, TLS 1.1, SSL 2.0, SSL 3.0) are explicitly disabled on all Platform servers;
  • TLS 1.3 is prioritized where supported by both client and server, as it offers improved security and performance over TLS 1.2;
  • Only strong, modern cipher suites are enabled — weak ciphers (such as RC4, DES, 3DES, export-grade ciphers) are disabled to prevent protocol downgrade attacks.

31.3 HTTP Strict Transport Security (HSTS)

The Platform implements HTTP Strict Transport Security (HSTS) with an appropriate max-age directive. HSTS instructs browsers that have previously visited the Platform to always use HTTPS for all future connections — even if the user types "http://" in the address bar or clicks an http:// link. This provides protection against:

  • SSL stripping attacks that attempt to downgrade connections from HTTPS to HTTP;
  • Cookie hijacking on networks where an attacker controls the network layer;
  • Accidental transmission of data over unencrypted connections.

31.4 Certificate Pinning (Android Applications)

Where technically appropriate and feasible, Indo Pakhtoon Tech Android applications implement certificate pinning or network security configuration to further strengthen the security of network connections made by the app. Certificate pinning restricts the application to communicating only with servers presenting certificates issued by a specific, trusted certificate authority — preventing attacks where a compromised root certificate authority issues fraudulent certificates for our domains.

31.5 Public Wi-Fi Usage Advisory

While Indo Pakhtoon Tech's TLS implementation protects your data even on untrusted networks, users are advised to exercise general caution when using the Platform on public Wi-Fi networks. In particular:

  • Always verify that the address bar shows a padlock icon and "https://" before submitting any information;
  • Consider using a reputable VPN service when accessing sensitive features (such as Google Sign-In) on public networks;
  • Be aware that public Wi-Fi networks may be monitored by their operators — while TLS protects content, metadata (such as the fact that you are visiting Indo Pakhtoon Tech) may still be visible to the network operator.
ℹ️ Android Network Security:

Indo Pakhtoon Tech Android applications are configured with a network_security_config.xml that enforces HTTPS-only communication and disables cleartext (unencrypted HTTP) traffic. This means our Android apps will refuse to communicate over unencrypted connections — providing a technical guarantee of encryption at the application level, independent of the device's overall network settings.

Anti-Spam & Abuse Protection

Detailed protocols and technical measures applied by Indo Pakhtoon Tech to prevent spam, bots, DDoS attacks, API abuse, and all forms of malicious automated activity

Indo Pakhtoon Tech is committed to maintaining a safe, stable, and high-quality experience for all legitimate users of the Platform. ℹ️ Privacy Note on Abuse Prevention:

Some abuse prevention measures necessarily involve processing technical data such as IP addresses, request frequency patterns, and device fingerprints. This processing is carried out strictly under the legal basis of Legitimate Interest — specifically, the legitimate interest of Indo Pakhtoon Tech in protecting the Platform's integrity, security, and availability for all users. Such processing is proportionate, time-limited, and does not involve any unnecessary collection of personal data.

39.1 Bot Detection & Mitigation

Automated bot traffic — including web scrapers, content harvesters, credential stuffing bots, and vulnerability scanners — represents a significant threat to Platform availability and data integrity. Indo Pakhtoon Tech deploys the following bot detection and mitigation mechanisms:

  • Behavioral Analysis: Incoming traffic is analyzed for behavioral patterns characteristic of automated bots, including abnormal request frequencies, non-human navigation sequences, absence of standard browser rendering behaviors, and anomalous timing patterns between requests. Traffic exhibiting these characteristics is flagged for further analysis;
  • User-Agent Filtering: Requests from known malicious bot user-agents — as identified through threat intelligence databases and our own observed patterns — are automatically rejected at the network edge before reaching the application layer;
  • CAPTCHA Challenges: Where appropriate — such as on contact form submissions, donation confirmation flows, and account creation endpoints — CAPTCHA challenges (including Google reCAPTCHA v3) are deployed to distinguish human users from automated bots with minimal disruption to genuine users. Google reCAPTCHA processes certain behavioral signals to generate a risk score, governed by Google's Privacy Policy;
  • Honeypot Fields: Certain forms on the Platform include invisible honeypot fields that are not visible to human users but are filled in automatically by bots — triggering automatic rejection of the submission without alerting the bot;
  • JavaScript Challenge: Where technically appropriate, JavaScript-based challenges verify that the client is a genuine web browser capable of executing client-side code — a check that most simple bots cannot pass.

39.2 Rate Limiting & Throttling

Rate limiting is one of the most effective defenses against both automated abuse and accidental overload from legitimate users. Indo Pakhtoon Tech implements rate limiting across all publicly accessible endpoints:

  • Per-IP Rate Limiting: Requests from a single IP address are limited to a reasonable number per minute/hour consistent with legitimate human usage patterns. Requests exceeding this threshold trigger temporary throttling — initially slowing responses, then returning HTTP 429 (Too Many Requests) errors, and ultimately temporarily blocking the IP if abuse persists;
  • API Endpoint Rate Limiting: Any API endpoints exposed by the Platform are individually rate-limited based on their expected legitimate usage patterns. Rate limits are designed to be generous enough to accommodate all legitimate use cases while blocking automated abuse;
  • Progressive Backoff: Rate limiting is implemented with progressive backoff — meaning that the response penalty increases proportionally with the severity and duration of abuse, rather than applying an immediate hard block that might affect legitimate users sharing an IP address (such as users on corporate or educational networks);
  • Temporary vs. Permanent Blocks: Most rate limit violations result in temporary blocks that expire after a defined cooling-off period. Only persistent, severe, or clearly malicious abuse patterns result in longer-term IP blocks.

39.3 DDoS Attack Protection

Distributed Denial of Service (DDoS) attacks — in which large volumes of traffic from many sources are directed at a target to overwhelm it and make it unavailable to legitimate users — are addressed through the following layered defenses:

  • Network-Level DDoS Mitigation: Indo Pakhtoon Tech's hosting infrastructure includes network-level DDoS protection provided by the hosting provider, which absorbs and filters volumetric attack traffic before it reaches the application servers. This protection operates transparently and does not affect the experience of legitimate users under normal conditions;
  • Anycast Network Diffusion: Where CDN (Content Delivery Network) infrastructure is used for serving static assets, Anycast routing distributes incoming traffic across multiple geographically distributed nodes, making volumetric DDoS attacks significantly less effective by diffusing the attack across the network;
  • Traffic Scrubbing: During active DDoS incidents, traffic scrubbing may be applied — routing all incoming traffic through specialized filtering infrastructure that identifies and drops attack packets while passing legitimate traffic through to the application servers;
  • Automatic Scaling: Where cloud hosting infrastructure supports auto-scaling, application resources are automatically expanded during traffic spikes to maintain availability for legitimate users even during attack conditions.

39.4 API Abuse Prevention

Any APIs or programmatic interfaces exposed by the Platform are protected against abuse through the following specific measures:

  • Authentication Requirements: All non-public API endpoints require valid authentication tokens. Unauthenticated requests to protected endpoints are rejected with HTTP 401 (Unauthorized) responses;
  • Token Validation: Authentication tokens are validated on every request — expired, revoked, or malformed tokens are rejected immediately;
  • Request Payload Validation: All API request payloads are validated against strict schema definitions — malformed requests, injection attempts (SQL injection, XSS payloads, command injection), and oversized payloads are rejected at the input validation layer before reaching business logic;
  • Audit Logging: All API requests are logged with sufficient detail to enable forensic investigation of abuse incidents. Log data is retained for the periods described in the Data Retention Policy (Section 13) and is accessible only to the Developer;
  • Anomaly Detection: Automated monitoring identifies unusual API usage patterns — such as systematic data enumeration, credential stuffing attempts, or unusual access to sensitive endpoints — and triggers alerts for manual review and response.

39.5 Email Spam Prevention

Indo Pakhtoon Tech implements the following technical measures to prevent our email communications from being classified as spam and to protect users from receiving unsolicited communications:

  • SPF (Sender Policy Framework): DNS SPF records are configured to specify which mail servers are authorized to send emails on behalf of Indo Pakhtoon Tech domains, preventing email spoofing;
  • DKIM (DomainKeys Identified Mail): All outgoing emails from Indo Pakhtoon Tech are digitally signed using DKIM, allowing recipients' mail servers to verify that the email genuinely originated from our authorized servers;
  • DMARC (Domain-based Message Authentication): A DMARC policy is published for Indo Pakhtoon Tech domains, instructing receiving mail servers on how to handle emails that fail SPF and DKIM checks — protecting users from phishing emails impersonating Indo Pakhtoon Tech;
  • Opt-In Only Communications: Marketing and non-essential email communications are sent only to users who have explicitly opted in. Transactional emails (such as support responses and refund confirmations) are sent only in direct response to user-initiated actions.

45.2 Device Fingerprinting — Explicit Prohibition

Device fingerprinting is a technique that combines multiple device and browser characteristics — such as screen resolution, installed fonts, browser plugins, hardware configurations, and rendering behaviors — to create a unique "fingerprint" that can identify and track a specific device across sessions and websites, even without cookies or other stored identifiers. Indo Pakhtoon Tech explicitly and categorically prohibits the following fingerprinting practices:

  • Canvas fingerprinting — using the HTML5 Canvas API to extract device-specific rendering characteristics for tracking purposes;
  • WebGL fingerprinting — using WebGL rendering information to create device-specific tracking identifiers;
  • Audio context fingerprinting — using the Web Audio API to extract hardware-specific audio processing characteristics;
  • Font enumeration fingerprinting — systematically detecting installed fonts to create a device-specific tracking profile;
  • Hardware sensor fingerprinting — using accelerometer, gyroscope, or other device sensor readings to create tracking identifiers;
  • Battery status fingerprinting — using battery level and charging status data to create persistent tracking identifiers;
  • IP address tracking combined with other signals to create persistent cross-session user profiles without consent.
🔴 Zero Fingerprinting Commitment:

Indo Pakhtoon Tech will never implement, enable, or permit any form of device fingerprinting on the Platform — whether through our own code or through third-party scripts. Privacy Architecture Summary

A technical overview of how Indo Pakhtoon Tech's Platform is architecturally designed to minimize data collection and maximize user privacy by default

Privacy is most effectively protected not through legal promises alone but through architectural choices — designing systems so that unnecessary data collection is technically impossible, not merely prohibited. This section provides a technical summary of the privacy-protective architectural choices made in the design of the Indo Pakhtoon Tech Platform.

51.1 Privacy-by-Architecture Principles Applied

  • Stateless Anonymous Sessions: The Platform serves the vast majority of its content and tool functionality through stateless HTTP responses that do not require or create any server-side session state for unauthenticated users. This means that for anonymous users, there is simply no user session record on our servers to compromise, misuse, or breach;
  • Client-Side Processing Architecture: Wherever technically possible, computation is performed in the user's browser or on the user's device rather than on our servers. This "client-side first" architecture means that user data — such as tool inputs — physically never leaves the user's device, making server-side data protection irrelevant for that data category;
  • Authentication Delegation: By delegating all authentication to Google OAuth 2.0, the Platform's architecture eliminates the need to ever handle, store, or protect user passwords. This removes an entire class of privacy and security risk from our systems entirely — rather than trying to protect passwords, we have designed a system where passwords simply do not exist in our infrastructure;
  • Payment Architecture Isolation: By using UPI's native payment flow, the Platform's architecture ensures that payment credentials never enter our system at any point. The payment flow is architecturally isolated to the user's UPI app and the NPCI banking infrastructure — our servers receive only the transaction reference number, not any payment authentication data;
  • Data Compartmentalization: Different categories of data are stored in separate, access-controlled systems — analytics data, account data, and operational logs are compartmentalized so that a breach of one system does not automatically expose all categories of data;
  • Minimal Surface Area: The Platform exposes the minimum number of public-facing endpoints, APIs, and interfaces necessary to deliver its Services — reducing the attack surface available to potential adversaries and the number of potential data leakage points.

51.2 Open-Access Architecture — Privacy Benefit

The decision to make the Platform open-access — requiring no registration or login for core features — is not only an accessibility and user experience choice, it is also a profound privacy architecture decision. When users are not required to create accounts, there is no account database to breach, no user profile to expose, and no registration data to misuse. The privacy protection for the overwhelming majority of Platform users is structural — they simply have no personal data in our systems to protect.

ℹ️ Privacy Through Simplicity:

The most powerful privacy protection Indo Pakhtoon Tech offers is structural simplicity: a Platform that does not need your personal data to serve you has no incentive, reason, or technical mechanism to collect it. When the Platform's business model does not depend on harvesting user data, privacy protections are not in tension with commercial interests — they are aligned with them.
